## 1. HTTP 状态码全局约定（修复问题 #24）

### 1.1 状态码适用条件（补充进 04 §1.2，前后端与测试统一断言）

| HTTP | 适用条件 | 响应体 | 示例 |
|---|---|---|---|
| 200 | 同步操作成功，含业务警告 | `code=OK` 或业务警告码（如 `RPM-OUT-001`） | 查询、成果疑似重复仍保存 |
| 201 | 同步创建资源成功 | `code=OK` + 资源 ID | 创建草稿、上传完成 |
| 202 | 异步流程已受理，非最终结果 | `code=ACCEPTED` + `instanceId`/`versionId` + 轮询入口 | 申报提交、支出提交、验收提交、导出创建 |
| 204 | 成功但无返回体 | 无 | 删除草稿、标记已读 |
| 409 | 版本冲突/重复操作；**幂等重放返回首次结果时用 200** | `code=RPM-COMMON-409` 或首次结果 | 重复回调返回 200 + 首次结果 |

### 1.2 202 响应体规范

```json
{
  "code": "ACCEPTED",
  "message": "已受理，进入审批流程",
  "data": {
    "instanceId": "uuid",
    "versionId": "uuid",
    "status": "IN_REVIEW",
    "pollUrl": "/api/v1/workflow/instances/{instanceId}"
  },
  "trace_id": "..."
}
```

- 前端收到 202 后跳转详情页轮询 `pollUrl`（间隔 3s，最多 20 次）或等待通知。
- 幂等：同一 `Idempotency-Key` 重复提交返回 **200 + 首次结果**，不重复启动流程。
- 支付回调等外部回调接口一律返回 **200**（含首次结果重放），不使用 202。

## 2. 报表与导出接口（修复问题 #1：RPT-01～RPT-05）

### 2.1 接口目录（`rpm-reporting`，只读）

| 方法 | 路径 | 用途 | 权限 | 需求 |
|---|---|---|---|---|
| GET | `/reports/project-summary` | 项目概况统计（RPT-01） | `report:project:view` | RPT-01 |
| GET | `/reports/progress-timeliness` | 里程碑/报告及时率（RPT-02） | `report:progress:view` | RPT-02 |
| GET | `/reports/funding-summary` | 经费执行统计（RPT-03） | `report:funding:view` | RPT-03 |
| GET | `/reports/output-summary` | 成果统计（RPT-04） | `report:output:view` | RPT-04 |
| GET | `/reports/risk-overview` | 领导风险视图（RPT-06，P1） | `report:risk:view` | RPT-06 |
| POST | `/exports` | 创建导出任务（202） | 复用对应报表权限 + `report:export` | RPT-05 |
| GET | `/exports` | 我的导出任务列表 | `report:export` | RPT-05 |
| GET | `/exports/{exportId}` | 导出任务进度与结果 | `report:export`（仅本人或管理员） | RPT-05 |
| GET | `/exports/{exportId}/download` | 下载导出文件（短期签名重定向） | 同上 + 下载时二次校验 | RPT-05 |

**导出授权规则**：导出请求体 = 对应报表的查询参数原样传递，后端强制复用同一授权服务与过滤条件，禁止前端传自定义范围；`report:export` 缺失时返回 403。

### 2.2 RPT-01 项目概况统计

`GET /reports/project-summary?deptId=&status=&fundingSource=&dateFrom=&dateTo=&page=&size=`

**查询 DTO（ProjectSummaryQuery）**：`deptId`（含子部门，按数据范围求交）、`status`（项目状态多选）、`fundingSource`、`dateFrom/dateTo`（立项时间范围）、分页。

**指标口径**：

| 指标 | 口径 |
|---|---|
| 项目总数 | 按筛选条件的未删除项目数；`TERMINATED` 单列不合并 |
| 各状态分布 | `group by status` 计数 |
| 总预算/支出 | `sum(total_budget)` / `sum(paid_amount)`，来源 `mv_funding_summary` |
| 成员数 | 去重 `user_id`（`ACTIVE` 成员） |
| 按部门汇总 | `dept_path` 前缀聚合，下钻字段：`deptId` |

**统计时点**：物化视图 `mv_project_summary.data_as_of`，响应体必须返回 `dataAsOf`；前端展示"数据截至 {dataAsOf}"。

**下钻**：每行返回 `projectId/projectNo/projectName`，点击跳转 `GET /projects/{projectId}`（权限校验同详情）。

**响应 VO（ProjectSummaryVO）**：

```json
{
  "dataAsOf": "2026-11-17T03:00:00+08:00",
  "items": [{
    "projectId": "uuid", "projectNo": "RPM-2026-0001", "projectName": "...",
    "status": "EXECUTING", "deptId": "uuid", "deptName": "...",
    "memberCount": 8, "milestoneTotal": 12, "milestoneCompleted": 5,
    "reportTotal": 6, "reportLateCount": 1,
    "totalBudget": 1000000.00, "totalPaid": 350000.00
  }],
  "total": 1
}
```

**空结果**：无项目时返回空 `items` + `total=0` + `dataAsOf`（HTTP 200，不是 404）。

### 2.3 RPT-02 里程碑/报告及时率

`GET /reports/progress-timeliness?deptId=&projectId=&period=QUARTER&dateFrom=&dateTo=`

**指标口径**：

| 指标 | 口径 |
|---|---|
| 里程碑按时完成率 | 分母=`actual_date` 落在统计期内的里程碑；分子=`actual_date <= current_plan_date` |
| 里程碑延期率 | 分子 = 有已批准延期申请且 `actual_date > 原plan_date` 的里程碑（区分"批准延期"与"未批准超期"两列） |
| 报告及时率 | 分母=统计期内应提交报告数（按报告周期配置生成）；分子=`late_flag=false` 的提交版本 |
| 迟报分布 | 按部门聚合 `late_flag=true` 计数 |

**数据来源**：`milestone`、`milestone_delay_request`（区分批准/未批准）、`progress_report_version.late_flag`（迟报唯一事实来源，主档状态不含 LATE，见修复 #23）。

### 2.4 RPT-03 经费统计

`GET /reports/funding-summary?deptId=&projectId=&budgetCategory=&executionRateFrom=&executionRateTo=&dateFrom=&dateTo=`

**指标口径**：来源 `mv_funding_summary`，按项目×科目行返回 `totalBudget/totalReserved/totalApproved/totalPaid/availableBalance/executionRate`；支持按 `executionRate` 区间筛选（如执行率低于 30% 预警）。

**下钻路径**：报表行 → `GET /funding/projects/{projectId}/budget`（预算明细）→ `GET /funding/expenses?projectId=&budgetLineId=`（支出明细），沿用 05 已有接口，授权同源。

### 2.5 RPT-04 成果统计

`GET /reports/output-summary?deptId=&projectId=&outputType=&dateFrom=&dateTo=`

**指标口径**：来源 `mv_output_summary`；**去重规则**：全院口径按 `output.id` 去重（一篇论文无论关联几个项目计 1）；项目口径按关联计数（`cross_project_count` 标注多项目关联）。类型分布 `group by output_type`；审核状态分布 `approved_count/pending_count`。

### 2.6 RPT-05 导出任务

**创建**：`POST /exports`

```json
{
  "reportType": "FUNDING_SUMMARY",
  "format": "XLSX",
  "queryParams": { "deptId": "uuid", "dateFrom": "2026-01-01" }
}
```

- 响应 **202** + `{exportId, pollUrl: "/exports/{exportId}"}`；`Idempotency-Key` 头必传，同键返回 200 + 首次任务。
- `reportType ∈ {PROJECT_SUMMARY, PROGRESS_TIMELINESS, FUNDING_SUMMARY, OUTPUT_SUMMARY}`。
- 后端校验：`queryParams` 反序列化为对应 Query DTO 并执行与实时查询**完全相同**的授权与过滤。

**进度查询**：`GET /exports/{exportId}` → `{status: PENDING|RUNNING|SUCCESS|FAILED, progress, fileExpiresAt, errorMessage}`。

**下载**：`GET /exports/{exportId}/download` → 校验任务 `SUCCESS`、文件未过期（生成后 7 天）、下载人 = 创建人或审计角色 → 302 重定向到 ≤5 分钟短期签名；每次下载写审计 `EXPORT_DOWNLOADED`。

**失败重试**：FAILED 任务可 `POST /exports/{exportId}/retry`（新任务复用原查询）。

**`wf_template_version.definition` JSON Schema（发布校验标准）**：

```json
{
  "type": "object",
  "required": ["nodes", "edges"],
  "properties": {
    "nodes": {"type": "array", "minItems": 1, "items": {
      "type": "object",
      "required": ["nodeKey", "name", "assigneeType", "actionScope"],
      "properties": {
        "nodeKey": {"type": "string", "pattern": "^[A-Z][A-Z0-9_]{1,63}$"},
        "assigneeType": {"enum": ["ROLE", "USER", "DEPT_ROLE", "INITIATOR_SUPERVISOR", "EXPRESSION"]},
        "assigneeValue": {"type": "string"},
        "condition": {"type": "string"},
        "actionScope": {"type": "array", "items": {"enum": ["APPROVE","REJECT","RETURN","DELEGATE"]}},
        "slaHours": {"type": "integer", "minimum": 1}
      }
    }},
    "edges": {"type": "array", "items": {
      "type": "object", "required": ["from", "to", "onAction"],
      "properties": {"from": {"type": "string"}, "to": {"type": "string"},
        "onAction": {"enum": ["APPROVE","REJECT","RETURN"]},
        "condition": {"type": "string"}}
    }}
  }
}
```

- 发布校验项：Schema 合法、`nodeKey` 唯一、边引用的节点存在、起止节点连通、`condition` 表达式仅引用白名单变量（`amount`、`projectType`、`fundingSource`、`deptId`）、同一节点多出边条件互斥且覆盖完整。
- **历史实例兼容**：运行中实例继续绑定创建时的 `template_version_id`，不受新版本发布影响；模板停用前必须无运行中实例。

## 4. 通用文件接口（修复问题 #4：`rpm-file`）

### 4.1 接口目录

| 方法 | 路径 | 用途 | 权限 |
|---|---|---|---|
| POST | `/files/direct` | 小文件直传（≤5MB，multipart） | 登录用户 + 业务用途校验 |
| POST | `/files/upload-sessions` | 初始化分片上传（202/201） | 同上 |
| POST | `/files/upload-sessions/{sessionId}/parts/{chunkNo}` | 上传分片（幂等重传） | 会话创建人 |
| GET | `/files/upload-sessions/{sessionId}` | 查询已传分片（断点续传） | 会话创建人 |
| POST | `/files/upload-sessions/{sessionId}/complete` | 完成上传，合并→扫描→生成 `file_id`（202） | 会话创建人 |
| POST | `/files/upload-sessions/{sessionId}/abort` | 中止会话 | 会话创建人 |
| GET | `/files/{fileId}/meta` | 元数据（名称/大小/类型/scan_status/sha256） | 按 `file_ref` 业务授权 |
| GET | `/files/{fileId}/download` | 鉴权下载：302 → ≤5 分钟短期签名 | 业务授权服务 |
| GET | `/files/{fileId}/preview` | 预览（PDF/图片内联，其余 422） | 同下载 |
| GET | `/files/{fileId}/scan-status` | 病毒扫描状态查询 | 上传人或业务授权 |
| DELETE | `/files/{fileId}` | 逻辑删除（置 `DELETED`，有 `file_ref` 引用时拒绝） | 上传人或 `file:manage` |

### 4.2 关键规则

- **所有业务模块（申报附件、支出凭证、成果证明、验收材料）只保存 `file_id`**；文件本体与哈希仅在 `rpm-file`。
- 上传完成后 `scan_status=PENDING`，扫描通过才 `AVAILABLE`；未通过置 `QUARANTINED` 并通知上传人；业务绑定文件时校验 `status=AVAILABLE`，否则 `RPM-FILE-001`。
- 分片上传：`chunk_size` 默认 8MB；重复分片按 `(session_id, chunk_no)` 幂等跳过；会话 48 小时过期由 `FileSessionCleanupJob` 中止。
- 下载签名：`file_download_grant` 表记录；业务撤销授权（如支出退回、成员移除）时批量 `REVOKE`，旧签名立即失效；签名有效期 ≤5 分钟。
- 直传与完成接口均写审计 `FILE_UPLOADED`；下载写 `FILE_DOWNLOADED`（含业务上下文）。

| 用例 | 断言 |
|---|---|
| TC-FILE-101 | 大于 5MB 文件走直传返回 `RPM-FILE-002` |
| TC-FILE-102 | 分片重复上传同一 chunkNo 返回上次 etag，不重复存储 |
| TC-FILE-103 | 断点续传：中断后查询已传分片，仅补传缺失分片 |
| TC-FILE-104 | 扫描未通过文件被业务绑定时返回 `RPM-FILE-001` |

| TC-FILE-108 | 会话过期后 complete 返回 422，S3 multipart 已中止 |

## 8. 变更类型契约矩阵（修复问题 #15：CHG-01）

### 8.1 通用结构

入口保持 `POST /projects/{projectId}/changes`，请求体为 **受控 discriminated union**：

```json
{ "changeType": "PERIOD", "payload": { ... }, "reason": "...", "evidenceFileIds": [] }
```

后端按 `changeType` 反序列化为独立 Cmd 并执行类型专属校验；`payload` 非法结构返回 400（禁止自由 JSON 落库）。

### 8.2 六类变更矩阵

| changeType | 必填字段（payload） | 附件要求 | 审批模板（bizKey） | 允许项目状态 | 生效动作（批准后同事务） |
|---|---|---|---|---|---|
| PERIOD | `newStartDate`,`newEndDate`（≥原区间、在项目周期内） | 可选 | `CHANGE_PERIOD` | EXECUTING | 新基线版本 + 里程碑日期联动重算 |
| PI | `newPiUserId`,`handoverNote` | 必填交接说明 | `CHANGE_PI` | EXECUTING | 新基线 + `project_member` 角色切换 + 待办/风险转移（复用交接逻辑） |
| MEMBER | `changes[]: {userId, projectRole, action ∈ ADD/REMOVE}` | 可选 | `CHANGE_MEMBER` | EXECUTING | 新基线 + 成员表生效区间切换（受 `exc_project_member_overlap` 约束） |
| OBJECTIVE | `objectives[]`（新目标/里程碑集合，含判定标准） | 必填论证材料 | `CHANGE_OBJECTIVE` | EXECUTING | 新基线（目标+里程碑整体替换，原值进历史版本） |
| BUDGET | `budgetVersionDraftId`（已保存的调整草稿） | 必填调整说明 | `CHANGE_BUDGET` | EXECUTING | 预算新版本 EFFECTIVE + `budget_balance` 初始化 + 资金事件 `ADJUST` |
| PARTNER | `partners[]: {unitName, role, action ∈ ADD/REMOVE/UPDATE}` | 合作协议文件必填（ADD/UPDATE） | `CHANGE_PARTNER` | EXECUTING | 新基线 + 合作单位表更新 |

### 8.3 统一规则

- 变更审批中：沿用当前生效基线（不预占用）；批准回调、新基线创建、旧基线置 `SUPERSEDED` 同事务（受 `uk_project_baseline_effective` 兜底，修复 #7）。
- 退回：申请单 `RETURNED`，可修改后重新提交（新版本号）。
- 越权：仅 PI 与科研管理可发起对应类型；`OBJECTIVE/BUDGET` 变更需科研管理会签。

## 10. 资金事件投影矩阵（修复问题 #17，补充 05 §1.2）

余额投影字段：`reserved_amount`（占用）、`approved_unpaid_amount`（批准未付）、`paid_amount`（已付）。

| 事件 | 触发场景 | reserved | approved_unpaid | paid | 约束与审批依据 |
|---|---|---|---|---|---|
| RESERVE | 支出提交进入审批 | +amount | — | — | 余额检查在事件前 |
| RELEASE | 撤回/拒绝/取消（未批准） | −amount | — | — | 不得低于 0 |
| APPROVE | 审批通过 | −amount | +amount | — | 与 RESERVE 配对 |
| PARTIAL_PAY | 部分支付回调 | — | −paid | +paid | `paid ≤ approved_unpaid` 前置；累计 partial ≤ approved |
| PAY | 全额支付回调 | — | −approved | +approved | 支付完成置 PAID |
| CANCEL | 支付后取消剩余额度 | — | −剩余approved | — | 仅 APPROVED_UNPAID/PARTIALLY_PAID 可发起 |
| REFUND | 外部退款回调（钱退回院账户） | — | — | −refund | `refund ≤ paid`；产生正向资金回流记录，需对账凭证 |
| REVERSE | 冲正（内部记账错误整体撤销） | 视原事件反向冲抵 | 同左 | 同左 | 仅当日 T+1 内、原事件无后续事件时允许；需财务终审 |
| ADJUST | 预算调整/特批通过 | ±delta（目标：`budget_balance.approved_amount` 侧，经预算调整版本生效后修正批准额） | — | — | 依据=预算调整版本或特批单；不直接动 paid |

**REFUND 与 REVERSE 边界**：REFUND 是外部真实资金回流（有银行凭证，走回调+对账）；REVERSE 是内部错误更正（无外部资金流，走财务终审）。两者均不可叠加于已 REVERSE 的事件。

**投影重建**：`paid_amount` 由 `PAY/PARTIAL_PAY/REFUND/REVERSE` 按符号重放；`reserved/approved` 由 `RESERVE/RELEASE/APPROVE/CANCEL/REVERSE` 重放；全量重放与实时投影误差必须为 0（TC-FUND-035 扩展覆盖全部九类事件）。

### 10.1 验证用例（补入 07）

| 用例 | 断言 |
|---|---|
| TC-FUND-110 | 每类事件单笔应用后三字段值与矩阵一致 |
| TC-FUND-111 | 全量重放九类事件混合序列，投影误差=0 |
| TC-FUND-112 | PARTIAL_PAY 超出 approved_unpaid 被拒绝 |

| TC-FUND-114 | REVERSE 作用于已有后续事件时被拒绝 |

## 11. 支付回调并发幂等（修复问题 #18，补充 05 §3.3 实现规则）

- 事务内执行 `INSERT INTO payment_record ... ON CONFLICT (external_payment_no) DO NOTHING RETURNING id`；未返回行即并发重复：**同事务查询原记录**，比对载荷一致后返回首次结果（HTTP 200），载荷不一致返回 `RPM-INT-004`。

- 处置归档清单模板：终止决议审批件、截止时点基线快照、已发生经费决算、已形成成果清单、未尽事项说明；材料哈希校验与接收流程同验收归档。
- 更正仅允许 `ADD_APPEND`（追加条目）与 `DESC_CORRECTION`（目录描述更正），批准后由档案员执行追加操作并留痕；**已归档证据原文永不修改**（数据库触发器兜底，修复 #9）。
- 整包下载：manifest SHA-256 校验后打包，下载走 ≤5 分钟短期签名，每次写审计 `ARCHIVE_DOWNLOADED`。
