# 设计决策说明

> 面向读者：评审这套 MVP 的工程师与技术负责人。
> 本文回答三个问题：**这套系统到底在解决什么问题；为什么做这些、不做哪些；核心设计思路是什么。**
> 所有决策都在「一个人、有限的交付时间、可运行的 MVP」约束下做出，我会在每一处诚实标注：哪些是深思熟虑的设计，哪些是有意识的边界，哪些是已知的债。

---

## 0. 我的立场：科管系统的第一性不是功能多，而是不出错、可追溯

在动手之前，我先问了自己一个问题：**一个科研院所，为什么放着 Excel 和 OA 不用，要专门建一套科管系统？**

答案不是「缺一个项目 CRUD」。科研管理的真实痛点是：

1. **责任说不清**。一个项目从申报到验收要过科研处、院系、财务、专家评审多个环节，出了问题（经费超支、成果归属、延期未报）时，靠邮件和纸质单据无法回答「谁在什么时候基于什么信息做的决定」。
2. **钱的口径不统一**。预算在科研处是一套数、财务账上是另一套数、项目负责人自己心里还有一套数。月底对账靠人肉拉表。
3. **过程证据散落**。申报书改了八稿只留最后一稿；中期检查要的材料临时补；验收时才发现交付物没有留痕。
4. **越权访问常态化**。项目预算、成员薪酬分摊、未公开成果，这些敏感数据在共享盘里谁都能看。

所以我把这套系统的定位写成一句话：**建立一条以项目为主线的业务链，让每次申报有版本、每项审批有责任、每笔经费有口径、每个风险有处置、每项成果有出处、每次验收有证据。**

这个定位直接决定了我的优先级排序：**安全与可追溯 > 业务闭环完整性 > 使用体验 > 功能数量**。下文所有决策都可以回溯到这个排序。

## 1. 先定义问题：这套系统到底在管什么

我按真实科研院所（单院多部门、约 1000～3000 用户、年新增项目 ≤2000）的业务建模，把「项目全生命周期」拆成一条主线加三个平台能力：

**一条业务主线**（对应真实院所的项目形态：纵向/横向/院级项目）：

```
申报(版本化) → 审批(Flowable) → 立项(自动) → 执行(报告/交付物/里程碑)
     ↑                                              ↓
     └── 变更/延期/终止(独立审批) ←── 经费(预算/支出/对账) ← 成果(登记/查重/关联)
                                                    ↓
                                                 验收(预留)
```

**三个平台能力**（任何业务模块都要用，必须先做对）：

- **IAM**：认证 + 功能权限（RBAC）+ 数据范围（行级）+ 字段脱敏；
- **工作流**：审批模板版本化、条件路由、回调分发——审批是科管系统变化最频繁的部分；
- **审计**：关键动作与业务同事务落审计，非关键动作走 Outbox 异步补写。

## 2. 范围决策：做了什么、没做什么、为什么

### 2.1 做了（且做到生产深度）的

| 能力 | 做到什么深度 | 为什么值得这个深度 |
|---|---|---|
| 数据权限 | 5 种数据范围（全院/部门/PI 本人/项目成员/临时授权）在后端 SQL 层统一注入，列表、详情、附件、导出、异步任务同一套逻辑；并有真 PostgreSQL 的集成测试逐条验证 | 这是科管系统的安全生命线。评审专家需要「临时授权看一个项目」这类精细控制，前端过滤是自欺欺人 |
| 审计 | 关键动作（提交/审批/资金/授权）与业务同事务：审计写失败业务即回滚；非关键动作 Outbox + 幂等补写 + 指数退避 + DEAD 人工介入 | 纪检调档、经费巡查时要能重建任何一次决策。Outbox 只写不消费等于没有异步审计，所以我补上了完整的补写任务 |
| 经费 | 预算版本化（生效版本唯一）；支出全状态机；资金事件**只追加**（应用层 + 数据库触发器双保险）；财务对账（导入→校验→差异处理说明必填） | 财务对账的本质是「资金流可重建」。UPDATE 掉历史记录的系统在第一次审计时就失去公信力 |
| 审批 | Flowable 7 引擎 + 自建 `wf_*` 业务投影表；模板版本化；自审批阻断（SOD）；审批轨迹含每轮动作与意见 | 院所的回避制度是刚性的（PI 不能审自己的申报）；审批链按项目类型频繁调整，硬编码状态机维护不动 |
| 幂等与并发 | 提交走「查幂等键→锁→锁内复查→乐观锁」四步；资金事件唯一约束兜底；全部写路径带 version 乐观锁，冲突返回 409 | 真实场景：审批人在手机上双击、网络超时重试、两个人同时处理同一单。没有幂等的系统会在第一次高峰日出事 |
| 认证 | JWT 双 token，**类型严格隔离**（refresh 不能当 access 用）；登录防枚举（占位哈希等耗时）；生产环境密钥缺失 fail-fast 拒绝启动 | 这些是我在自审时发现并修复的：初版 refresh token 可以直接调业务 API，生产密钥会静默回退到仓库里的开发密钥——这两类问题在安全评审里是一票否决 |

### 2.2 明确不做（或只留接口）的，以及为什么

| 不做 | 理由 |
|---|---|
| **验收模块（rpm-acceptance 为空模块）** | 验收依赖执行与成果数据积累，MVP 阶段做验收表单是表演。我选择把执行/成果/审计做扎实，验收在 `rpm-acceptance` 预留模块位与数据模型 |
| **消息通知（rpm-notification 为空模块）** | 院所已有邮件/企微/飞书等消息平台，自建站内信是重复建设且没人看。通知是典型的「集成项」而非「自建项」，Outbox 的事件管道已预留 |
| **报表中心（rpm-reporting 为空模块）** | 我建了 4 个物化视图作为读模型并接入了定时刷新，但**不假装有报表**。做几个静态图表很容易，做对的口径很难——口径必须等真实使用反馈 |
| **SSO 单点登录** | 需求阶段锁定 OIDC，本地账号作为 V1 降级路径已实现。SSO 联调依赖院方身份平台，属于环境问题不是代码问题；`iam_login_log.login_type` 已区分 LOCAL/SSO/REFRESH |
| **财务系统直连** | 真实院所的财务接口条件从来都不确定（这是我在需求假设里明确标注的 A3）。所以 V1 做标准模板导入 + 对账 + 差异处理，支付回调验签 fail-closed（没配密钥接口就拒绝服务而不是裸奔） |
| **移动端原生 App** | 领导审批的移动需求用响应式 Web 覆盖；原生 App 的推送、加固、发版成本对 MVP 不成立 |
| **电子实验记录/仪器管理** | 「管项目责任与证据，不管实验本身」——这是与 ELN 系统的边界，混做两个领域只会都做不好 |
| **微服务/引入 MQ** | 见架构决策 §3.1/3.2 |

**不做清单比做了一样重要**：面试题说「不按功能数量打分」，我完全认同——科管系统失败案例里最常见的就是「什么都有、什么都浅、没人敢用它记账」。

## 3. 架构决策

### 3.1 模块化单体，而不是微服务

千人级院内系统、年项目量 ≤2000、院内私有化部署（往往只有一个运维甚至没有运维）。这个规模下微服务带来的分布式事务、链路排查、部署复杂度是纯成本。但我没有做成大泥球：

- **16 个 Maven 模块**按业务域拆分（iam/application/workflow/project/execution/funding/output/file/audit/...），每个模块内部 DDD 四层（api/application/domain/infrastructure）；
- **跨模块只允许走端口（Port）**：funding 想知道项目信息，注入 `ProjectXxxPort` 而不是 import 对方 repository；查询侧的 CQRS 例外有明确注释与只读约束；
- 这等于给未来的服务化留好了切割线：模块边界即服务边界。**先保证事务一致和低运维，等规模或团队结构逼你拆的时候再拆，而不是反过来。**

### 3.2 不引入 MQ：PostgreSQL 事务内 Outbox + 进程内调度

可靠的异步（审计补写、未来的通知/集成）用「与业务同事务写 outbox 表 + 后台任务领取投递」实现：

- 领取用 `FOR UPDATE SKIP LOCKED`，多实例部署不重复消费；
- 幂等用 outbox 的 `event_id` 作为目标表主键 + `ON CONFLICT DO NOTHING`——「领取成功但标记成功前崩溃」的重放不会产生重复行；
- 失败按 1m→5m→15m→1h 退避，5 次进 DEAD 等人工处理。

私有化环境里，**少一个基础组件就少一类故障和一份采购审批**。院方 PostgreSQL 已经是可信的事实来源，把它用足。

### 3.3 流程引擎选 Flowable，而不是自研状态机

有人会说「一个两节点审批链自己写 if-else 就够了」。但真实科管的审批是：按项目类型路由不同链、条件分支（金额超阈值加签）、会签/或签、驳回重报、委托代理、超时转办、模板本身要版本化。这些是 Flowable 的基本盘，自研等于重新发明一个残缺的 BPMN。我的做法是：

- Flowable 只做**编排**（ACT_* 表独立 schema，由 Flyway 管理版本），业务状态投影到自建 `wf_instance/wf_task` 表——审批中心、已办、我发起的、轨迹全部查自己的表，不跟引擎内部表耦合；
- 审批结果通过 `ApprovalResultHandler` 回调分发回业务模块（申报/支出/变更各自处理审批副作用），引擎与业务解耦。

### 3.4 存储选型：让每个组件只干自己最擅长的事

- **PostgreSQL 16 是唯一事实来源**：13 个 Flyway 迁移、显式外键与 CHECK 约束、不可变触发器、部分唯一索引（如「同一业务版本只允许一个 RUNNING 实例」）——**数据库约束是应用代码之外的最后防线**，审计/资金这些表我不允许应用层 bug 越过 DB 约束；
- **Redis 只是缓存不是事实**：权限快照 5 分钟 TTL，读失败自动降级回源数据库、写失败只告警不阻断——Redis 挂掉系统照常运行，这符合「院内环境组件随时可能没人管」的现实；
- **MinIO + 预签名 URL**：文件上传做四层校验（扩展名白名单/MIME/大小/魔数），下载签发 ≤300 秒预签名 URL，**应用不代理文件流**——200MB 申报书不该经过 JVM 堆。

### 3.5 版本化一切

真实科管的铁律是「改过的东西要能看到改了什么」。所以：申报版本（content_hash 防无变化提交）、预算版本（生效版本唯一）、支出版本、成果版本、周期报告版本、审批模板版本。项目立项时拍基线（baseline），后续变更走独立审批并留痕。

## 4. 安全设计：这是我投入最重的一块

按威胁从外到内列，每条都对应到实现与验证方式：

| 威胁 | 设计 | 验证 |
|---|---|---|
| 越权访问业务数据 | 数据范围在 SQL 片段统一注入 + 应用服务二次授权（双层）；5 种范围含时间维度（成员过期即失效、临时授权有过期时间） | 真 PG 集成测试 7 个用例逐一断言可见集 |
| 账号枚举 / 撞库 | 登录失败统一文案；用户不存在时用占位 BCrypt 哈希保持等耗时；登录日志记录失败原因供审计 | 单测 + 代码路径审查 |
| token 泄漏放大 | access 8h / refresh 7d **类型隔离**（filter 只认 access，refresh 接口只认 refresh）；生产密钥缺失拒绝启动 | 集成冒烟：refresh 调业务接口返回 401 |
| SQL 注入 | 全部 mapper `#{}` 参数化，动态条件（含行级过滤）也是参数化占位；LIKE 转义 | 代码扫描零 `${}` 业务拼接 |
| 越权下载附件 | 下载必须过授权服务签发短期 grant（≤300s），签名与业务授权双重校验 | 单测覆盖拒绝/放行路径 |
| 业务写重放/双击 | 幂等键四步提交 + 唯一约束兜底 + 乐观锁 409 | 134+ 单测含幂等重放用例 |
| 利益冲突 | 自审批阻断（SOD）、申报利益冲突声明（COI）表、审批委托校验 | WorkflowTaskAppServiceTest SOD 用例 |
| 审计丢失 | 关键审计与业务同事务（失败即回滚）；非关键 Outbox 补写 | Outbox 补写任务 + 幂等单测 |
| 配置泄漏 | 生产凭据全部环境变量注入，缺失 fail-fast；仓库不含任何生产密钥 | prod profile 启动路径审查 |

**已知边界（诚实清单）**：logout 未做服务端撤销（靠 8h TTL 收敛，接入 Redis 黑名单是下一步）；文件业务引用（`file_ref`）的写入点预留但未在所有业务模块铺开，当前下载口径为「上传人可见 + 资源上下文授权」；大文件上传暂为内存校验（200MB 上限下可接受，流式分片是明确的改进项）。

## 5. 我如何用 AI 交付这套系统（AI Native 的实践）

这套系统约 9 万行后端 + 1.2 万行前端，全部由我在 AI 辅助流水线上交付。我的做法不是「让 AI 写」，而是**把工程纪律前置成 AI 可执行的约束**：

1. **需求先行、决策显式**：先产出带「事实/决策/假设」标注的需求文档（假设 A1~A5 都写了验证方式与失效影响），再产出 9 份技术方案，经两轮评审（D1~D4）整改后才进入编码；
2. **硬规则清单**：禁止跨模块写表、禁止 `setStatus` 裸改状态、禁止事务内外部 HTTP、金额必须 BigDecimal/numeric(18,2)、资金只追加、数据库变更只新增 Flyway 脚本——这些规则写进每个批次的生成上下文，违反即打回；
3. **机器可验证的验收**：每个阶段产出「验证用例清单」（TC 编号可追溯到测试方法名），最终 1067 个测试里，审批主链路、schema 迁移、行级权限都是**真 PostgreSQL + 真 Flowable** 的集成测试，不是 mock 的自我安慰；
4. **AI 生成 + 我做安全自审**：交付前我做了一轮深度安全评审，发现并修复了 JWT 类型混用、密钥静默回退、登录计时侧信道、审计 Outbox 只写不消费、文件引用后必 403 等问题——**AI 大幅提速，但安全判断必须是人兜底**。

这条流水线本身（需求→技术方案→评审→任务拆解→批次生成→验证）的产物完整保留在 `docs/` 下，可复核全过程。

## 7. 如果给我下一个迭代

按优先级：① logout 服务端撤销（Redis 黑名单）+ 文件引用写入点铺开；② 验收模块落地（复用执行/成果/审计已有数据）；③ 财务直连接口（验签与幂等框架已就位）；④ OIDC 对接院方身份平台；⑤ 报表中心消费物化视图。你看，这个清单里的每一项，都是今天「不做」清单里带着理由的预留——**这就是我说的：不做不是砍掉，是想清楚了再动。**
