# 设计决策说明

## 1. 设计前提与系统目标

本项目按单个科研院所、多部门协作的规模设计，假设用户数为 1000～3000，年新增项目不超过 2000，采用院内私有化部署。基于这个前提，设计上优先保证数据一致性、权限隔离和过程可追溯，而不是追求功能数量或分布式架构的复杂度。

Excel 和通用 OA 可以完成信息收集与通用审批，但难以同时处理以下问题：

- 项目经过申报、审批、执行、变更和验收等多个环节后，需要能够还原每次操作的时间、责任人、处理意见和当时使用的数据版本。
- 预算、支出和财务对账需要有统一口径，历史资金记录不能因后续修改而失去依据。
- 申报书、周期报告、交付物和成果材料需要保留版本，不能只保存最后一份文件。
- 项目预算、成员薪酬分摊和未公开成果等数据需要按部门、项目成员和授权期限控制访问范围。

因此，系统围绕项目全生命周期建立业务主线，并将设计优先级确定为：**安全与可追溯性、业务闭环完整性、使用体验、功能数量**。后续的范围和架构取舍都遵循这个顺序。

## 2. 业务范围

### 2.1 业务主线与公共能力

业务主线覆盖纵向、横向和院级项目：

```text
申报（版本化）→ 审批（Flowable）→ 立项（自动）→ 执行（报告、交付物、里程碑）→ 验收（预留）
```

执行过程中还包含三类关联业务：

- 项目变更、延期和终止，均走独立审批；
- 经费管理，包括预算、支出和财务对账；
- 成果管理，包括成果登记、查重和项目关联。

各业务模块共用三项基础能力：

1. **IAM**：认证、RBAC 功能权限、行级数据范围和字段脱敏。
2. **工作流**：审批模板版本化、条件路由和审批结果回调。
3. **审计**：关键动作与业务数据在同一事务中写入审计记录，非关键动作通过 Outbox 异步补写。

### 2.2 本次已实现的部分

**数据权限**

实现了全院、部门、PI 本人、项目成员和临时授权五种数据范围，在后端 SQL 层统一注入过滤条件。列表、详情、附件、导出和异步任务使用同一套权限逻辑，避免不同入口出现可见范围不一致。权限规则通过真实 PostgreSQL 集成测试逐项验证。

**审计**

提交、审批、资金和授权等关键动作与业务操作处于同一事务，审计写入失败时业务一并回滚。非关键动作使用 Outbox 异步补写，并实现了消费、幂等、指数退避和 DEAD 状态处理，避免事件只写入表而无人处理。

**经费**

预算采用版本管理，同一时间只允许一个生效版本；支出按状态机流转；资金事件只追加，应用层和数据库触发器共同限制修改历史记录。财务对账支持模板导入、数据校验和差异处理，差异处理说明为必填项。

**审批**

使用 Flowable 7 负责流程编排，同时建立 `wf_*` 业务投影表。审批模板支持版本管理，审批人校验包含自审批阻断（SOD），审批轨迹保留每轮动作和意见。业务页面主要查询投影表，减少对 Flowable 内部表的依赖。

**幂等与并发**

提交操作按“查询幂等键、加锁、锁内复查、乐观锁更新”的顺序处理，资金事件另由数据库唯一约束兜底。写路径使用 `version` 乐观锁，冲突时返回 409，用于处理双击、超时重试和多人同时处理同一业务单的情况。

**认证**

采用 access token 和 refresh token 双令牌，并严格校验令牌类型，refresh token 不能调用业务接口。登录失败使用统一提示，用户不存在时仍执行占位哈希校验，缩小响应时间差异。生产环境缺少密钥时直接拒绝启动，不回退到开发配置。

## 3. 架构决策

### 3.1 使用模块化单体

在用户规模、项目量和私有化部署条件下，微服务会增加分布式事务、链路排查和部署维护成本，而当前业务规模并不需要独立扩缩容。因此，系统采用模块化单体，但通过模块边界控制依赖关系：

- 后端拆分为 16 个 Maven 模块，包括 iam、application、workflow、project、execution、funding、output、file、audit 等；模块内部按 api、application、domain、infrastructure 分层。
- 跨模块访问通过 Port 完成。例如 funding 需要项目数据时依赖 `ProjectXxxPort`，不直接引用对方 Repository。查询侧的 CQRS 例外有单独注释，并保持只读。
- 业务边界与模块边界保持一致，后续确有独立部署需求时，可以沿现有边界拆分。

当前方案优先保证本地事务一致性和部署简单，是否服务化应根据后续规模和团队边界决定。

### 3.2 使用 PostgreSQL Outbox，不引入独立 MQ

审计补写以及后续通知、外部集成都需要可靠的异步事件。当前实现是在业务事务中写入 Outbox 表，再由进程内调度任务领取并处理：

- 使用 `FOR UPDATE SKIP LOCKED` 领取事件，支持多实例运行；
- 使用 Outbox 的 `event_id` 作为目标表主键，并通过 `ON CONFLICT DO NOTHING` 保证幂等；
- 事件在“已领取但尚未标记成功”时发生进程崩溃，可以通过重放恢复，不会写入重复记录；
- 失败重试间隔依次为 1 分钟、5 分钟、15 分钟和 1 小时，重试 5 次后进入 DEAD 状态，等待人工处理。

现有 PostgreSQL 已能满足这一事件量，暂不额外引入 MQ，可以减少部署组件和运维工作。若后续吞吐量或跨系统事件规模明显增长，再评估独立消息中间件。

### 3.3 使用 Flowable，并将业务状态与引擎解耦

科管审批不只是固定的两节点状态流转，还涉及按项目类型路由、金额条件加签、会签或或签、驳回重报、委托代理、超时转办和模板版本管理。自研这些能力会形成一套不完整且难以维护的流程引擎，因此选用 Flowable。

Flowable 只负责流程编排，`ACT_*` 表使用独立 schema，并由 Flyway 管理版本。业务侧建立 `wf_instance`、`wf_task` 等投影表，审批中心、已办、我发起的和审批轨迹均查询业务表。审批完成后，由 `ApprovalResultHandler` 将结果分发到申报、支出或变更模块，各模块自行处理后续业务状态。

### 3.4 存储与文件方案

- **PostgreSQL 16**：作为业务数据的事实来源。当前有 13 个 Flyway 迁移脚本，使用外键、CHECK 约束、不可变触发器和部分唯一索引约束关键数据。例如，同一业务版本只允许存在一个 RUNNING 实例。数据库约束用于防止应用层缺陷破坏审计和资金数据。
- **Redis**：只用于缓存，不保存不可恢复的业务事实。权限快照 TTL 为 5 分钟；读取失败时回源数据库，写入失败只记录告警，不阻断业务。Redis 不可用不影响系统核心功能。
- **MinIO**：文件通过预签名 URL 上传和下载。上传校验包括扩展名白名单、MIME、大小和魔数；下载授权有效期不超过 300 秒。文件流不经过应用服务，避免大文件占用 JVM 内存和服务带宽。

### 3.5 业务数据版本管理

申报、预算、支出、成果、周期报告和审批模板均保留版本。申报内容使用 `content_hash` 避免无变化重复提交，预算只允许一个生效版本。项目立项时形成 baseline，后续变更通过独立审批处理，并保留变更前后的记录。

版本管理的目的不是保存多份相同数据，而是让审批、执行和验收能够引用当时实际使用的业务内容。

## 4. 安全设计与已知限制

主要威胁、实现方式和验证方式如下：

| 威胁 | 实现方式 | 验证方式 |
|---|---|---|
| 越权访问业务数据 | SQL 层统一注入数据范围，应用服务再次授权；五种数据范围包含成员有效期和临时授权有效期 | 使用真实 PostgreSQL 的 7 个集成测试用例检查可见数据集 |
| 账号枚举、撞库 | 登录失败统一提示；用户不存在时执行占位 BCrypt 校验；登录日志记录失败原因 | 单元测试和代码路径审查 |
| token 泄漏后的影响扩大 | access 有效期 8 小时，refresh 有效期 7 天；两类 token 严格隔离；生产密钥缺失时拒绝启动 | 集成冒烟测试验证 refresh token 调用业务接口返回 401 |
| SQL 注入 | Mapper 使用 `#{}` 参数化，动态条件和行级过滤同样使用参数占位，LIKE 条件进行转义 | 扫描确认业务 SQL 未使用 `${}` 拼接 |
| 越权下载附件 | 下载前由授权服务签发不超过 300 秒的 grant，同时校验签名和业务权限 | 单元测试覆盖拒绝和放行路径 |
| 写请求重放、重复点击 | 幂等键处理、数据库唯一约束和乐观锁共同控制，版本冲突返回 409 | 134+ 单元测试，包含幂等重放场景 |
| 利益冲突 | 自审批阻断（SOD）、申报利益冲突声明（COI）和审批委托校验 | `WorkflowTaskAppServiceTest` 中的 SOD 用例 |
| 审计记录丢失 | 关键审计与业务同事务，非关键审计通过 Outbox 补写 | Outbox 消费与幂等测试 |
| 配置和凭据泄漏 | 生产凭据通过环境变量注入，缺失时 fail-fast，仓库不保存生产密钥 | 检查 prod profile 启动路径 |

当前仍有以下限制：

1. logout 尚未实现服务端令牌撤销，目前依靠 access token 的 8 小时有效期控制风险，后续计划增加 Redis 黑名单。
2. `file_ref` 的写入点已经预留，但尚未覆盖所有业务模块。当前下载权限按“上传人可见，并通过资源上下文授权”处理。
3. 大文件上传目前在内存中完成校验，200 MB 上限下可以运行，但流式校验和分片上传仍需改进。

这些限制不影响当前主流程演示，但上线前应按实际部署环境逐项评估。

## 5. AI 辅助开发与质量控制

本项目约包含 9 万行后端代码和 1.2 万行前端代码，开发过程中使用了 AI 辅助生成代码和文档。为避免生成结果偏离设计，实际执行时增加了以下约束和检查：

1. **先确定需求和技术方案。** 需求文档区分事实、决策和假设，A1～A5 假设均注明验证方式和失效影响；随后编写 9 份技术方案，经过两轮评审和 D1～D4 问题整改后再进入编码。
2. **将工程规则写入生成上下文。** 包括禁止跨模块写表、禁止绕过状态机直接调用 `setStatus`、禁止在事务内调用外部 HTTP、金额统一使用 BigDecimal 和 `numeric(18,2)`、资金事件只追加、数据库变更只能新增 Flyway 脚本。违反规则的代码不进入后续验收。
3. **按测试用例验收。** 每个阶段维护验证用例清单，TC 编号可以追溯到测试方法。审批主链路、schema 迁移和行级权限均使用真实 PostgreSQL、真实 Flowable 做集成测试，不只依赖 mock。
4. **单独进行安全自审。** 自审中发现并修复了 JWT 类型混用、生产密钥静默回退、登录计时侧信道、审计 Outbox 只写不消费，以及文件引用导致下载 403 等问题，再补充相应测试。

需求、方案、评审、任务拆解和验证材料均保留在 `docs/` 目录，便于对照检查。AI 生成结果只作为实现起点，最终以代码审查和测试结果为准。

## 7. 后续迭代顺序

下一迭代计划按以下顺序推进：

1. 实现 logout 服务端撤销，并将 `file_ref` 写入点覆盖到各业务模块；
2. 基于现有执行、成果和审计数据实现验收模块；
3. 在财务接口条件明确后接入直连，复用现有验签和幂等机制；
4. 对接院方 OIDC 身份平台；
5. 在报表口径确认后，基于已有物化视图实现报表中心。

这个顺序先补齐安全和数据边界，再扩展业务功能，避免在基础约束不完善时继续增加入口。
