# 设计决策说明

这份文档说明这个 MVP 的主要技术决策：系统解决什么问题、做和没做什么、为什么这样选。先交代约束：一个人、有限的交付时间、要求可运行。所有决策都在这个前提下做出，有意识的取舍和已知的债在文末单独列出。

## 1. 对问题的基本判断

科研院所放弃 Excel 和 OA、专门建科管系统，通常不是缺一个项目 CRUD，而是几件事撑不住了：

1. 责任说不清。一个项目从申报到验收要过科研处、院系、财务、专家评审多道环节，出了问题（经费超支、成果归属纠纷、延期未报）时，靠邮件和纸质单据查不到"谁在什么时候基于什么信息做的决定"。
2. 钱的口径对不上。科研处一套预算数、财务账上一套、PI 自己心里一套，月底靠人肉拉表对账。
3. 过程证据散落。申报书改了八稿只留最后一稿，中期检查的材料临时补，验收时发现交付物没有留痕。
4. 敏感数据裸奔。项目预算、成员薪酬分摊、未公开成果，在共享盘里谁都能看。

所以系统定位是：以项目为主线把业务串起来，每一步留版本、留责任、留口径。由此确定优先级——安全和可追溯排第一，业务闭环完整性第二，使用体验和功能数量靠后。后面每个决策都能回溯到这个排序。

按单院多部门、约 1000～3000 用户、年新增项目不超过 2000 的规模建模，业务主线是：

```
申报(版本化) → 审批(Flowable) → 立项(自动) → 执行(报告/交付物/里程碑)
     ↑                                              ↓
     └── 变更/延期/终止(独立审批) ←── 经费(预算/支出/对账) ← 成果(登记/查重/关联)
```

另有三个所有业务模块都要用的平台能力，必须先做对：IAM（认证、功能权限、数据范围、脱敏）、工作流（模板版本化、条件路由、回调分发）、审计（同事务写入加异步补写）。

## 2. 范围决策

### 2.1 做到的部分

| 能力 | 深度 | 说明 |
|---|---|---|
| 数据权限 | 5 种数据范围（全院/部门/PI 本人/项目成员/临时授权）在后端 SQL 层统一注入，列表、详情、附件、导出、异步任务走同一套逻辑 | 行级过滤是这类系统的安全底线。评审专家"临时授权看单个项目"是真实需求，前端过滤不可接受。配了真 PostgreSQL 的集成测试逐条验证 |
| 审计 | 关键动作与业务同事务，审计写失败业务即回滚；非关键动作走 Outbox 异步补写，幂等领取加指数退避，5 次失败转 DEAD 等人工处理 | 纪检调档、经费巡查要能重建任何一次决策。Outbox 只写不消费等于没有异步审计，所以补写了完整的消费端 |
| 经费 | 预算版本化，生效版本唯一；支出全状态机；资金事件只追加（应用层不暴露 update，数据库触发器兜底）；对账走导入→校验→差异处理，差异关闭必须填说明 | 财务对账的前提是资金流可重建。能 UPDATE 历史记录的系统，第一次审计就失去公信力 |
| 审批 | Flowable 7 编排，业务状态投影到自建 wf_instance/wf_task 表；模板版本化；自审批阻断；轨迹含每轮动作与意见 | 院所的回避制度是刚性的，PI 不能审自己的申报。审批链按项目类型频繁调整，硬编码状态机维护不动 |
| 幂等与并发 | 提交走"查幂等键→加锁→锁内复查→乐观锁"四步；资金事件有唯一约束兜底；写路径带 version，冲突返回 409 | 审批人双击、网络超时重试、两人同时处理一单，都是常态。没有幂等的系统第一次高峰日出事 |
| 认证 | JWT 双 token 且类型严格隔离（refresh 不能当 access 用）；登录失败统一文案，账号不存在时用占位哈希保持等耗时；生产环境密钥缺失直接拒绝启动 | 这几条是交付前自审发现并修复的。初版 refresh token 能直接调业务 API、生产密钥会静默回退到仓库里的开发密钥，这两类问题过不了安全评审，也不应该过 |

### 2.2 没做的部分

| 不做 | 理由 |
|---|---|
| 验收模块（rpm-acceptance 空模块） | 验收依赖执行和成果数据的积累，MVP 阶段做验收表单没有意义。执行、成果、审计做扎实，验收留模块位和数据模型 |
| 消息通知（rpm-notification 空模块） | 院所一般已有邮件/企微/飞书，自建站内信是重复建设。Outbox 的事件管道已经预留 |
| 报表中心（rpm-reporting 空模块） | 建了 4 个物化视图做读模型并接入定时刷新，但不装样子摆几个图表。报表口径要等真实使用反馈才有意义 |
| SSO | 需求阶段锁定 OIDC，本地账号作为 V1 路径已实现。SSO 联调依赖院方身份平台，是环境问题不是代码问题，login_type 已区分 LOCAL/SSO/REFRESH |
| 财务直连 | 财务接口条件在院方环境从来不确定（需求文档里标为假设 A3）。V1 做标准模板导入、对账、差异处理；支付回调验签 fail-closed，没配密钥接口就拒绝服务而不是裸奔 |
| 移动端原生 App | 领导的移动审批用响应式 Web 覆盖。原生 App 的推送、加固、发版成本对 MVP 不成立 |
| 电子实验记录、仪器管理 | 边界：管项目责任与证据，不管实验本身。这是 ELN 系统的事 |
| 微服务、MQ | 见下节 |

不做清单和做了一样重要。科管系统失败案例里最常见的形态是"什么都有、什么都浅、没人敢用它记账"。

## 3. 架构决策

### 3.1 模块化单体，不是微服务

千人级院内系统、年项目量两千以内、私有化部署且往往没有专职运维。这个规模上微服务带来的分布式事务、链路排查、部署复杂度是纯成本。但也没有做成大泥球：16 个 Maven 模块按业务域拆分，每模块内部分 api/application/domain/infrastructure 四层；跨模块只允许走端口（Port），funding 要项目信息就注入 ProjectXxxPort，不 import 对方的 repository。查询侧允许跨表 JOIN 的 CQRS 例外，在 mapper 里有注释且限定只读。

这样模块边界就是将来服务化的切割线。先保证事务一致和低运维，等规模或团队结构逼着拆的时候再拆，而不是反过来。

### 3.2 不引入 MQ

可靠异步（审计补写、将来的通知和集成）用 PostgreSQL 事务内 Outbox 加进程内调度实现：领取用 FOR UPDATE SKIP LOCKED，多实例不重复消费；幂等靠 outbox 的 event_id 做目标表主键加 ON CONFLICT DO NOTHING，"领取成功但标记成功前崩溃"的重放不会产生重复行；失败按 1m→5m→15m→1h 退避。

私有化环境里少一个基础组件就少一类故障和一份采购流程。院方 PostgreSQL 已经是可信的事实来源，先用足。

### 3.3 流程引擎选 Flowable，不自研状态机

两节点审批链确实 if-else 就能写，但真实科管的审批是：按项目类型路由不同链、金额超阈值加签、会签或签、驳回重报、委托代理、超时转办、模板本身要版本化。这些是 Flowable 的基本盘，自研等于重做一个残缺的 BPMN。

用法上做了一个隔离：Flowable 只做编排（ACT_* 表独立 schema，Flyway 管理版本），业务状态投影到自建 wf_instance/wf_task 表。审批中心、已办、我发起的、轨迹全部查自己的表，不和引擎内部表耦合；审批结果通过 ApprovalResultHandler 回调分发回业务模块，引擎与业务解耦。

### 3.4 存储选型

- PostgreSQL 16 是唯一事实来源。13 个 Flyway 迁移，显式外键和 CHECK 约束、不可变触发器、部分唯一索引（同一业务版本只允许一个 RUNNING 实例）。数据库约束是应用代码之外的最后防线，审计和资金这些表不允许应用层 bug 绕过去。
- Redis 只是缓存。权限快照 5 分钟 TTL，读失败降级回源数据库，写失败只告警不阻断。Redis 挂掉系统照常运行，这符合院内组件随时可能没人管的现实。
- MinIO 加预签名 URL。上传做四层校验（扩展名白名单、MIME、大小、魔数），下载签发不超过 300 秒的预签名 URL，应用不代理文件流。200MB 的申报书不该过 JVM 堆。

### 3.5 版本化一切

真实科管的惯例是"改过的东西要能看到改了什么"。申报版本（带 content_hash，无变化不给提交）、预算版本、支出版本、成果版本、周期报告版本、审批模板版本；立项时拍基线，后续变更走独立审批留痕。

## 4. 安全设计

这是投入最重的部分，按威胁逐条列出，每条对应到实现和验证方式：

| 威胁 | 设计 | 验证 |
|---|---|---|
| 越权访问业务数据 | 数据范围 SQL 统一注入，应用服务二次授权；5 种范围含时间维度（成员过期即失效、临时授权有到期时间） | 真 PG 集成测试 7 个用例逐一断言可见集 |
| 账号枚举、撞库 | 登录失败统一文案；用户不存在时用占位 BCrypt 哈希保持等耗时；登录日志记失败原因供审计 | 单测加代码路径审查 |
| token 泄漏放大 | access 8h / refresh 7d 类型隔离，过滤器只认 access，刷新接口只认 refresh；生产密钥缺失拒绝启动 | 集成冒烟：refresh 调业务接口返回 401 |
| SQL 注入 | mapper 全部 #{} 参数化，动态条件（含行级过滤）也是参数化占位，LIKE 做转义 | 代码扫描，业务 SQL 零 ${} 拼接 |
| 越权下载附件 | 下载必须过授权服务签发短期 grant（不超过 300 秒），签名与业务授权双重校验 | 单测覆盖拒绝和放行路径 |
| 写操作重放、双击 | 幂等键四步提交、唯一约束兜底、乐观锁冲突返回 409 | 单测含幂等重放用例 |
| 利益冲突 | 自审批阻断（SOD）、申报利益冲突声明表、审批委托校验 | WorkflowTaskAppServiceTest 的 SOD 用例 |
| 审计丢失 | 关键审计与业务同事务；非关键走 Outbox 补写 | Outbox 补写任务加幂等单测 |
| 配置泄漏 | 生产凭据全部环境变量注入，缺失 fail-fast；仓库不含生产密钥 | prod profile 启动路径审查 |

已知边界，如实列出：logout 没做服务端撤销，靠 8h TTL 收敛，接 Redis 黑名单是下一步；文件业务引用（file_ref）的写入点预留但未在所有业务模块铺开，当前下载口径是上传人可见加资源上下文授权；大文件上传暂为内存校验，200MB 上限下可接受，流式分片是明确的改进项。

## 5. 交付过程

系统约 9 万行后端加 1.2 万行前端，在 AI 辅助的流水线上交付。做法核心是把工程纪律前置成 AI 可执行的约束，而不是放任生成：

1. 需求先行。先产出带"事实/决策/假设"标注的需求文档（假设 A1～A5 都写了验证方式和失效影响），再产出 9 份技术方案，经过两轮评审整改后才开始编码。
2. 硬规则清单。禁止跨模块写表、禁止 setStatus 裸改状态、禁止事务内外部 HTTP、金额必须 BigDecimal/numeric(18,2)、资金只追加、数据库变更只新增 Flyway 脚本。规则写进每个批次的生成上下文，违反即打回。
3. 机器可验证的验收。每阶段产出验证用例清单（TC 编号可追溯到测试方法名），最终 1068 个测试里，审批主链路、schema 迁移、行级权限都是真 PostgreSQL 加真 Flowable 的集成测试，不是 mock 的自我安慰。
4. 人工安全复审。交付前做了一轮深度评审，发现并修复了 JWT 类型混用、密钥静默回退、登录计时侧信道、审计 Outbox 只写不消费、文件引用后必 403 等问题。AI 大幅提速，但安全判断需要人兜底。

流水线各阶段的产物完整保留在 docs/ 下，全过程可复核。

## 7. 下一个迭代的优先级

1. logout 服务端撤销（Redis 黑名单）；文件引用写入点在各业务模块铺开
2. 验收模块落地，复用执行、成果、审计已有数据
3. 财务直连，验签与幂等框架已就位
4. OIDC 对接院方身份平台
5. 报表中心消费物化视图
